# electrobun.config.ts

## Worker packaging

Electrobun bundles only the main entry (`src/bun/index.ts`), so the task worker is bundled separately:

1. `bun run build:worker` bundles `src/worker/index.ts` with its dependencies (the Firestore SDK, gRPC and their proto files) into `dist/worker.js` with `bun build --target=bun`. `dev` and `build` run it after `build:view`, because Vite empties `dist/` first.
2. `build.copy` places it at `Resources/app/bun/worker.js`, next to the main bundle.
3. `src/bun/index.ts` resolves the path through `PATHS.RESOURCES_FOLDER`, not `import.meta.dir`: the launcher runs the main bundle in a Bun `Worker` thread and, for ASAR builds, from a copy in the temp directory.

The packaged app ships no `node_modules`; the bundle must stay self-contained. Tests run `src/worker/index.ts` from source instead.

## Built-in Google OAuth client

The config reads `google-oauth-client.local.json` next to it with `readBuiltInOAuthClient` (`built-in-oauth-client.md`) and sets `build.bun.define.BUILT_IN_OAUTH_CLIENT` to the client as JSON, or `null` when the file is absent. Hutch evaluates the config (top-level `await` and TypeScript imports work) for `electrobun prepare` (so `build:view`), `dev` and `build`, and forwards `define` to the main-process bundle only; the Vite webview build and the worker bundle never see it. An invalid file stops every one of those commands with `ConfigLoadFailed` and the reason.

The client secret therefore ships in plain text inside `Resources/app/bun/index.js` of the packaged app. Google treats the secret of a "Desktop app" client as not confidential; the sign-in uses PKCE and a loopback redirect. The file is git-ignored.

## App icon

`build.mac.icons` points at `icon.iconset/` (all sizes from 16 to 1024 px), which Electrobun turns into the `.icns` with `iconutil`. The PNGs are generated by `scripts/generate-icon.ts` (`bun run icon`, see `generate-icon.md`). Windows and Linux builds have no icon configured yet; the 1024 px PNG can serve as their source.

## Signing, notarization and updates

Not configured. A distributable build needs an Apple Developer ID certificate and notarization credentials in the `build.mac` signing settings, and auto-update needs a `release` base URL that hosts the update artifacts; see the README.
